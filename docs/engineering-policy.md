# 0xbot 工程协作规范

## 产品定位与范围

0xbot 是面向开发者和 AI 的 Web3 Provider 聚合网关。核心资产是同类能力的标准接口、Provider 适配和路由。REST API、SDK、MCP 共享业务能力；不另建大而全的 A2A 协议。

本文件适用于整个目录，子项目 AGENTS.md 补充各自规则。开始修改前阅读适用规则。用户已授权开始实施，当前交付首版查询聚合闭环；后续能力按阶段推进。

## 项目边界

- 后端语言确定为 Go，三个前端使用 TypeScript；后端按模块化单体组织，REST 与 MCP 共享 Go 应用用例。
- website：0xbot.org，中英文官网与开发者文档；默认英文，保留简体中文。
- app：app.0xbot.org，用户工作区、Key、Playground、调用记录与用量。
- dashboard：dashboard.0xbot.org，内部 Provider、路由、用户及计费管理。
- api：api.0xbot.org，标准 API、业务模块、Provider Adapter、MCP 和后台任务。
- 四个项目独立仓库、依赖、构建、配置及发布；禁止跨目录引用另一个项目的源码或直接访问其内部实现。
- 跨项目通过版本化 API 和生成客户端协作。共享设计令牌先有明确规范；只有出现稳定的重复需求时才提取可版本化公共包。

## 低耦合、高内聚

- 按业务能力组织模块：模块内聚合自己的用例、类型、规则和测试。通过显式公共接口访问其他模块，禁止深层导入与循环依赖。
- 每个模块有明确职责和数据所有权。禁止跨模块随意读写数据库表；通过所有者提供的接口协作。
- 业务规则不依赖 HTTP、MCP、具体 ORM、缓存客户端或 Provider SDK。外部依赖经窄接口注入，在组合入口装配。
- 路由、控制器、UI 组件保持薄层。参数转换、业务决策、供应商调用、持久化分别放在对应模块。
- 禁止堆积万能 service、通用 utils、巨型组件和带大量条件分支的 Provider 总处理器。以职责复杂度决定拆分，不机械追求文件数量。
- 优先简单直接的实现；不为假设需求引入插件系统、微服务或过度泛型。新增抽象必须说明已有复用点或明确隔离目的。
- 修改一个 Provider 应主要影响其适配器及契约测试；增加一个能力不应要求重写其他能力。

## 接口与状态

- 同类能力标准化输入、输出和错误；不同能力保留独立业务语义。共享请求 ID、Provider、费用、追踪等基础字段。
- Provider 原始响应不能成为默认公共接口。独有能力通过明确的扩展字段和能力声明暴露。
- OpenAPI 是 REST 契约来源；生成客户端不手改。破坏性变更需要版本策略和迁移说明。
- 金额不得使用浮点数计算；资产数量采用最小单位整数字符串或明确精度的十进制定点表达，携带资产与网络标识。
- 时间、地址、链标识、分页和错误码应有统一约定。对所有外部输入和上游响应进行必要验证。
- 查询与写操作分开设计。消息、支付、交易必须有幂等策略与显式状态；上游超时不等于失败，状态未知时不得盲目换 Provider 重复执行。
- 有副作用的接口说明重试边界。Webhook、队列消费者需支持重复与乱序事件。

## 安全与可观测性

- 用户注册与登录统一支持 Web3 钱包签名和 X 授权，首次成功认证自动创建账号；首版不提供邮箱密码注册。详见 docs/architecture.md 的身份与账号规则。
- 使用内部用户 ID 关联钱包和 X 身份；绑定必须验证当前账号和新增身份，不按昵称、头像或邮箱自动合并账号。登录签名不得兼作交易授权。
- 工作区权限在服务端逐请求验证；管理端权限独立校验。前端隐藏按钮不构成访问控制。
- API Key 按可验证摘要存储，创建时一次展示。上游凭证通过密钥引用或加密存储管理。
- 密钥、助记词、完整认证头和敏感消息不得进入仓库、日志或错误响应。AI 消息内容属于不可信输入，不能赋予操作权限。
- 超时、有限重试、速率限制和熔断策略明确配置。日志关联请求与操作 ID，记录 Provider、耗时与错误分类，并脱敏。
- 开发模拟数据必须显式标识，生产环境不能伪装真实成功。能力开放状态和价格展示必须与实际实现一致。

## 前端与国际化

- 官网、app、dashboard 统一米黄色暖色调，设计令牌见 docs/architecture.md。共享视觉语言，按各自信息密度设计布局。
- 对外 website 与 app 默认英文，保留简体中文及切换入口，app 尊重并记住 zh 偏好；新用户及不支持的语言回退 en。未来可增加 ko、ja，保留 locale 扩展结构但不提前启用。官网 /zh 提供中文页面，不跳转英文。管理后台 dashboard 和后端 api 的现有语言与功能不调整。
- 覆盖加载、空数据、错误、权限不足和成功状态；支持键盘操作、清晰焦点和可读对比度。
- API 访问集中于边界层，组件不直接拼接认证、Provider 参数或业务路由策略。

## 验证与维护

- 按风险测试：业务规则和状态转换用单元测试，Provider 用固定样本契约测试，持久化和权限用集成测试，关键用户流程用少量端到端测试。
- 必须覆盖租户隔离、撤销 Key、Provider 切换、计量去重以及有副作用请求的未知状态处理。
- 不为简单样式或实现细节堆砌测试。测试以可观察行为为目标，默认不依赖真实资金或不稳定上游。
- 各项目提供标准 lint、typecheck、test、build 命令。变更后运行适用检查，并明确未验证部分。
- 数据库变更通过迁移；上线前评估旧代码兼容性及恢复方式，不把破坏性迁移当成普通发布步骤。
- README 记录启动、环境变量、测试和部署；.env.example 仅含占位符。重要跨模块决策写 ADR，记录背景、决定和代价。
- 保留用户现有改动，避免无关重构。交付说明包含行为变化、验证结果和实际限制。

## 部署

- 已获用户授权通过 root SSH 操作指定服务器进行部署；每次先检查现有服务、端口和目录，保护无关服务。
- 初始采用独立容器和内部数据库网络；应用以非 root 运行。优先复用服务器已有反向代理。
- 发布具备版本标识、健康检查、日志、备份与回滚说明。根目录授权不意味着允许无关删除或不可恢复的数据变更。
